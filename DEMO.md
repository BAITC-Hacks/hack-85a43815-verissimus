# EnergyAI: демонстрация за две минуты

Цель показа — пройти от параметров исторического решения до почасового прогноза с зафиксированной коррекцией мощности, вызова инструмента агентом и отчёта, который можно открыть без интернета. Готовый пример: [docs/forecast_example.html](docs/forecast_example.html).

## Подготовка перед защитой

1. Установите зависимости и положите исходные CSV в `data/` по инструкции в README.
2. В терминале PowerShell из папки проекта запустите приложение:

   ```powershell
   .\.venv\Scripts\python.exe -m streamlit run app.py --server.port 8502
   ```

   Откройте `http://localhost:8502`. Оставьте терминал работающим.

3. Выберите в боковой панели:

   | Поле | Значение |
   |---|---|
   | Турбина | `turbine_1` |
   | Первый день прогноза | `01.02.2026` |
   | Горизонт, часы | `48` |
   | Момент решения (ISO 8601) | Оставить пустым |

4. Один раз нажмите **«Рассчитать выбранный прогноз»** и дождитесь результата. Это также подготовит погодный кеш для повторного показа. Период: 1 февраля 00:00 — 2 февраля 23:00 в принятом местном времени; момент решения по умолчанию — 31 января 23:00.
5. Проверьте **«Проверки прогноза»**. Условия пересчитываются по сохранённым строкам и метаданным; при ошибке или неподтверждённом условии выясните причину до показа. Не называйте эти проверки доказательством точности.
   В блоке **«Выполненный цикл: данные → архив → модель → проверка → отчёт»** можно показать `model.calibration`: калибровка должна быть применена для февральского решения, а её `available_at` — не позже момента решения. Она корректирует прогноз мощности, не ветер GFS.
6. Скачайте **«Скачать отчёт для жюри (HTML)»** и откройте файл в браузере. Это запасной материал для демонстрации при проблемах с интернетом. В отчёте нет внешних скриптов или CDN.
7. Если планируете показать AI-чат, заранее проверьте один запрос с настроенным локальным `OPENAI_API_KEY`. Основной расчёт кнопкой и отчёт не требуют ключа OpenAI. Не показывайте `.env` на экране.

Проверка уже сохранённой февральской выгрузки без сети и без API-ключа:

```powershell
.\.venv\Scripts\python.exe scripts\verify_submission.py
```

Для полной выгрузки ожидаются `status: success`, `row_count: 1344`, `daily_runs: 56`, `weather_sources_checked: 5376`. Проверяются контрольная сумма CSV, покрытие часов, диапазон мощности, происхождение погоды и временные ограничения. Это проверка согласованности сохранённых материалов, а не оценка ошибки за февраль.

Необязательная отдельная проверка настоящего AI-агента:

```powershell
.\.venv\Scripts\python.exe scripts\smoke_agent.py --run-live --scenario inspect
```

Эта команда намеренно делает реальные запросы OpenAI с локальным ключом и расходует API-кредиты: максимум три запроса, без автоматических повторов, до 700 выходных токенов на запрос. Она использует настоящий оркестратор и диспетчер инструментов; итог сохраняется в `artifacts/live_smoke.json`. Запускайте её только если хотите провести такую проверку. Команда не активирует выданные организаторами кредиты.

Для отдельной проверки запуска прогноза самим агентом замените `--scenario inspect` на `--scenario forecast`. Это ещё один запуск с отдельным лимитом до трёх платных запросов; результат сохраняется в `artifacts/live_smoke_forecast.json`.

Уже выполнены два реальных сценария: чтение сохранённого прогноза до установки калибровки и запуск нового прогноза с калибровкой через инструменты агента. Подтверждение без ключей хранится в `validation/agent_smoke.json`: всего 4 API-запроса, 11 487 токенов. Это проверка работы агента, не измерение качества его текстовых рекомендаций или точности мощности.

Мы воспроизводим историческое решение: используем только обучающие часы, завершённые к моменту решения, и проверяем временные метки выбранного архивного выпуска погоды». |

| 0:45–1:10 | Отправьте в чат подготовленный запрос ниже. | «LLM работает через расчётные инструменты: читает сохранённый результат и объясняет его. Числа поступают из модели и снимка прогноза». |

За февраль подготовлены 1344 строки для двух турбин; сохранённая выгрузка проверяется отдельной командой». |

Готовый запрос для чата:

> Вызови inspect_forecast для сохранённого прогноза. Кратко укажи турбину, период, момент решения, источник и выпуск погоды, среднюю нормализованную мощность. Объясни ограничения часового пояса и оценки точности. Не пересчитывай прогноз.

Время ответа внешнего API и загрузки погоды зависит от сети. Если ответ задержался, покажите уже сохранённый результат и журнал выполненной до защиты проверки. Не выдавайте заранее подготовленный ответ за новый живой вызов.

## Ответы на вероятные вопросы

**Почему значения безразмерные?** Организаторы предоставили нормализованную мощность, но не раскрыли базу и формулу нормализации. Прогноз сохраняет исходную шкалу `[0, 1]`.

**Откуда известен часовой пояс?** Он не указан в исходных метаданных. `Asia/Almaty` — явное допущение, которое можно изменить конфигурацией. В отчёте показаны местное время со смещением и UTC.

**Как исключается информация из будущего?** Обучающие часы должны завершиться к моменту решения; выпуск погодной модели и метки архивных объектов проверяются относительно того же момента. HTTP Last-Modified — свидетельство архива, а не независимое доказательство первого опубликования. Это ограничение открыто указано.

**Какова точность за февраль?** Фактической выработки за февраль в предоставленных CSV нет. Поэтому точность за февраль не измерена. Для оценки подхода используется отдельная историческая проверка на январе с простыми базовыми методами. Показывайте фактические результаты текущего README и блока **«Историческая проверка полного прогноза: модель и погода»**. Метрики блока **«Проверка модели при известной погоде»** относятся к другой задаче и не являются качеством прогноза на 24–48 часов.

**Что именно улучшилось?** Откройте **«Эффект калибровки на последующих январских прогнозах»**. Мы зафиксировали коррекцию прогноза мощности по решениям 1–16 января и проверили её на датах начала прогнозов 17–23 января. Общая MAE снизилась с 0,3221 до 0,2210 — на 31,38%; RMSE — с 0,4377 до 0,2862. Это январский эксперимент выбора модели, не февральская точность и не «точность 68,62%». Изменяется мощность после LightGBM, а не сам прогноз погоды.

**Это независимая проверка?** Коэффициенты оценивались только по более раннему периоду и были зафиксированы до расчёта оценочных метрик. Однако это короткий эксперимент выбора модели: 48-часовые окна перекрываются, а часть целевых часов пересекается с ранее просмотренным окном 24–30 января. В отчёте отдельно показаны 624 прогнозные строки с целевыми часами до 24 января. Эти строки тоже не являются полностью независимыми наблюдениями.

**Есть ли ухудшения?** Да. В дополнительном, ранее просмотренном окне 24–30 января общая MAE снизилась с 0,2357 до 0,2003, но на первых сутках для turbine_1 выросла с 0,1890 до 0,1933, для turbine_2 — с 0,1897 до 0,1984. Улучшение будущего периода не гарантировано. Предыдущая проверка сохранена в `validation/baseline/`, полное сравнение — в `validation/calibration/`.

**Почему повторная проверка ничего не изменила?** Исторический архив обычно остаётся неизменным. Обновление проверяет входы и сравнивает результаты; оно не должно искусственно менять график.

**Что улучшать дальше?** Проверить зафиксированную коррекцию мощности на новых сезонах и периодах, исследовать пространственную калибровку погоды к турбинам и интервалы неопределённости. Заявлять о дальнейшем улучшении можно только после временного сравнения без подгонки по будущим целевым часам.

Для воспроизведения январского эксперимента после демонстрации:

```powershell
.\.venv\Scripts\python.exe scripts\calibrate.py --output artifacts\calibration_reproduction
```

Команда требует исходные CSV и погодный архив/кеш, сохраняет кандидата и отчёты в `artifacts/`, но не заменяет установленный `models/power_calibration.json` автоматически. Её не нужно запускать во время двухминутной защиты.

## Краткое описание для формы сдачи

EnergyAI прогнозирует почасовую нормализованную мощность двух турбин на 24–48 часов. Архивные выпуски NOAA GFS, LightGBM, AI-чат с вызовом инструментов, проверка времени данных и повторный расчёт. Доступны CSV и автономный HTML-отчёт для жюри.
